# Publishing Management System

Planning and tracking tool for book production, built on the publisher's
_Masterproduktionsplan for bogudgivelser_ ([Research/](Research/)). Each book gets a live
production plan generated from the master plan; the focus is on handling delays and
postponements.

- Plan and roadmap: [docs/PLAN.md](docs/PLAN.md)
- Proposed default durations and dependencies (for client review): [docs/masterplan-defaults.md](docs/masterplan-defaults.md)

## Status

Stage A prototype: frontend only, data stored in the browser.

- Phase 0 (foundations), Phase 1 (scheduling engine) and Phase 2 (publications, table view,
  time machine) are done.
- Next: Phase 3, the interactive Gantt chart.

## Getting started

Requires Node 24+ and pnpm 11.

```bash
pnpm install
pnpm dev          # http://localhost:5173
```

## Using the app

The UI is in Danish.

- **Udgivelser** lists all books with release date, forecast, progress, health and next
  milestone. **Ny udgivelse** creates a book from the master plan and a desired release date.
- A book's page shows its plan as a table grouped by phase and track, with the columns from the
  PDF. Status and notes are edited inline. Clicking a current deadline opens a preview of what
  moves and what happens to the release, with four ways to handle the delay. Clicking an
  activity opens a side panel with dates, buffer, dependencies and history. Undo/redo works with
  the buttons or ⌘Z / ⇧⌘Z.
- **Masterplan** shows the template itself, read-only.

### Two datasets

Switch between them at the bottom of the sidebar.

| Dataset          | What it is                                                                                                                  |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **Demo**         | Five sample books at different stages, generated by simulation. Has the **Tidsmaskine** (time machine) for moving the date. |
| **Rigtige data** | Your own books. Always uses today's real date; nothing is simulated.                                                        |

The datasets are stored separately, so nothing done in the demo affects the real data.

### Tidsmaskine (demo only)

The bar at the top of the page sets the demo's date. Moving forward plays every demo book on:
work starts and finishes, some of it late, and overruns are rescheduled automatically. Moving
back rebuilds the demo data as of that date, so your own demo changes are lost (you are asked
first). The reset button rebuilds the demo as of today.

### Where data is stored

Everything is stored locally in the browser (IndexedDB, one database per dataset: `pms-demo` and
`pms-real`). It is not shared between browsers or machines. Use **Eksportér** / **Importér** on
the Udgivelser page to move a dataset as a JSON file; importing replaces the current dataset.
Clearing the site data in the browser deletes everything.

## Structure

```
apps/web          React 19 + Vite frontend (TanStack Router, Tailwind v4, shadcn/ui, Zustand)
packages/domain   Framework-free TypeScript: domain model, master plan template, working-day
                  calendar, scheduling engine, commands with undo/redo, simulation
docs/             Plan and client-facing notes
```

`packages/domain` has no browser dependencies, so the same code can run on a server in Stage B.
See [CLAUDE.md](CLAUDE.md) for a more detailed map of both packages.

## Conventions

- Code and identifiers in English; UI text in Danish via `apps/web/src/i18n/da.ts`.
- Dates are `YYYY-MM-DD` strings. Durations and template offsets are **working days**; offsets
  are relative to the release date (release = 0).
- The domain package never reads the system clock: anything that depends on "today" takes an
  explicit date. In the app, `apps/web/src/lib/clock.ts` is the only place that reads it.
- All plan changes go through domain commands, which log a change event and can be undone.
- The original deadline (_Oprindelig deadline_) is never overwritten.
- The master plan data file is hand-formatted (one line per activity) and excluded from Prettier.
- After adding or renaming a route file, run `pnpm dev` or `pnpm build` once to regenerate
  `routeTree.gen.ts` before typechecking.
